# ZeeSpare

Multi-tenant cloud SaaS for service parts planning (OEMs, distributors, multi-brand dealer groups in KSA, UAE, Qatar, Kuwait, Oman, Bahrain, Egypt, Jordan). Goal: match Syncron Service Parts Planning and go beyond it. The roadmap and build steps live in `docs/PLAN.md`.

## Rules for every session

- **Design and typography.** Read and follow [design.MD](design.MD) for every UI change. Items is the typography reference: use the shared type roles and shared sidebar; page-specific CSS must not change navigation, body or page-title font sizes at any breakpoint. Verify Dashboard ↔ Items navigation when changing application typography.
- **Language.** English is the primary language and the default locale. Arabic is optional, switched on per organization. Every user-facing string goes through next-intl message files: `apps/web/messages/en.json` is complete, `ar.json` is a stub and is deep-merged over English at request time. Use Tailwind logical utilities only (`ms-`, `me-`, `ps-`, `pe-`, `inset-s-`, `inset-e-`, `text-start`, `rounded-s-`, `border-s`), never `left`/`right`, `ml`/`mr`, `pl`/`pr`, `text-left`/`text-right`. `pnpm check:logical` enforces this; files under `src/components/ui` are generated by shadcn with `rtl: true` and are exempt.
- **Multi-tenancy.** Every business table has `organization_id uuid not null`, row-level security enabled, and policies based on the user's membership. No table ships without RLS and a pgTAP test proving users cannot read or write another organization's rows.
- **Data types.** Money is `numeric(18,3)` with a `currency char(3)` column (KWD, BHD, OMR and JOD use 3 decimals). Quantities are `numeric(18,3)`. Timestamps are `timestamptz` in UTC. Hijri dates are computed for display only, never stored as the source of truth.
- **Regional config lives in tables, not code:** weekend days per country (Fri-Sat for KSA, Qatar, Kuwait, Oman, Bahrain; Sat-Sun for UAE), VAT rates, public holidays, currencies.
- **Schema changes only through migrations** in `supabase/migrations` (`pnpm exec supabase migration new <name>`, `pnpm exec supabase db diff`). Never change the remote database by hand. Never push migrations to the hosted project yourself; tell the owner the command and they run it after review.
- **Secrets** only in `.env.local` (gitignored) and GitHub Actions secrets. `.env.example` holds names only. The secret key (`SUPABASE_SECRET_KEY`) is used only in server code, never in the browser. The repository is public.
- **Done means tested.** Every step ends with lint, typecheck and all tests passing, then a pull request with a short description of what changed and how to try it. One step per PR.
- If something needs a credential or a decision from the owner, stop and ask instead of guessing.

## Session protocol

Read this file and `docs/PLAN.md`, pull the latest `main`, and check which steps are merged. Start the next step in plan mode: propose the plan, wait for approval, build it on a new branch (`feat/step-N-<slug>`), make all tests pass, open a pull request. Stop after that one step.

## Conventions

- **Versions are pinned exactly.** TypeScript stays on 6.x until typescript-eslint supports the TypeScript 7 API. The Supabase CLI is a root devDependency (`pnpm exec supabase`) so local and CI match.
- **Locale.** No URL prefix. `src/i18n/request.ts` takes the `locale` cookie, else the active organization's `default_locale`, and honours `ar` only while the organization has `arabic_enabled` (`src/i18n/resolve.ts`). Arabic is handed to next-intl as `ar-u-nu-latn` or `ar-u-nu-arab` per the organization's `numbering_system` (`intlLocaleFor` in `src/i18n/config.ts`), and the time zone is its `effective_time_zone`. Anonymous requests never query the database. Date-only columns are formatted with `timeZone: 'UTC'` (`src/lib/format.ts`). `<html lang dir>` and the Base UI `DirectionProvider` are set in the root layout; the root `NextIntlClientProvider` receives only the client namespaces, so per-entity messages stay on the server. Use `useTranslations` in client and non-async components, `getTranslations` in async server code. Add new strings to `en.json` first; `ar.json` may lag.
- **UI.** shadcn components live in `src/components/ui` (Base UI primitives, style `base-nova`, `rtl: true`). Add with `pnpm dlx shadcn@4.21.4 add -c apps/web <name>` from the repo root; do not hand-edit them beyond what the CLI generated. App components live in `src/components`.
- **Supabase.** Server code uses `createClient()` from `src/lib/supabase/server.ts` (one per request); the browser uses `src/lib/supabase/client.ts`. Sessions are refreshed and routes guarded in `src/proxy.ts`; layouts and actions still verify through `requireClaims()` in `src/lib/auth/session.ts` (parsed claims incl. `org_id`/`org_role`), and `getActiveContext()` in `src/lib/organizations/context.ts` gives the active organization and the user's role from the database. The service-role client exists only in `src/lib/supabase/admin.ts` (`import 'server-only'`) for `auth.admin` calls. Env names: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (read lazily by `src/lib/env.server.ts`).
- **Auth.** Invitation-only: `[auth] enable_signup = false`; account creation remains invitation-driven. Password-recovery requests return neutral text for unknown addresses. Email + password on `/login`, with recovery at `/auth/forgot-password`; existing magic-link callbacks remain supported. Recovery tokens are consumed by a POST from `/auth/recover`, then `/auth/reset-password` reuses the authenticated password update. See `docs/industrial-studio-login.md` for owner-run recovery email-template and allow-list setup; sign-in links complete at `/auth/confirm` (token hash) or `/auth/callback` (PKCE code); invitation links complete at `/auth/invite` with a POST (mail gateways prefetch GET links), then `/auth/set-password` (skippable) and `/invitations/<id>`. `app.custom_access_token_hook` adds `org_id` and `org_role` (the active organization) to every JWT; the hook is enabled in `supabase/config.toml` locally and by the owner in the hosted Dashboard after `db push`. A changed `[auth]` block needs `pnpm db:stop && pnpm db:start`. Keep `[auth.email] enable_confirmations = true` (and "Confirm email" on in the hosted Dashboard): invitations are matched on `auth.users.email`, and with confirmations off an e-mail change takes effect immediately. Users with no resolvable active organization land on `/organizations`; switching calls `set_active_organization` then `refreshSession()` once, inside a Server Action only. Local email templates in `supabase/templates` must be mirrored into the hosted Dashboard by the owner.
- **Database.** Tenant tables carry `organization_id`, a surrogate `id` plus a natural `code` unique per organization, and a unique `(organization_id, id)` so children use composite foreign keys that cannot cross tenants. RLS predicates are set-based: `organization_id = any (array(select app.member_organizations()))` for select and `organization_id = any (array(select app.editable_organizations()))` (owner, admin, planner) for insert, update and delete. Never call a boolean function per row in a policy; Postgres evaluates it once per candidate row, while the array subquery is an InitPlan evaluated once per statement and `= any` on it is an index condition, so unscoped queries read only the member's rows. The six set helpers (`member`, `editable`, `admin`, `approving`, `unscoped` `_organizations()` and `scoped_locations()`) intersect `memberships` with the token's `org_id` claim when present, so a claim can only narrow access; `app.is_member(org)` and `app.can_edit(org)` ignore the claim and serve single-organization checks in code and tests. Branch scoping is an additive RESTRICTIVE policy on `locations` and `demand_history` (`... or <id> = any (array(select app.scoped_locations()))`); `supabase/tests/0005_tenant_invariants.test.sql` names every allowed helper explicitly and fails on any other predicate shape. Writes to `organizations`, `memberships`, `membership_locations`, `organization_invitations` and `user_settings` go only through the security-definer RPCs (`create_organization`, `invite_member`, `accept_invitation`, ...), which raise `MQ401/403/404/409/422/429` SQLSTATEs mapped in `src/lib/rpc-errors.ts`; `authenticated` has no insert/update/delete privilege on those tables, and no API role has TRUNCATE, REFERENCES, TRIGGER or MAINTAIN on any public table. RPCs that check a count before writing (last owner, organization cap, invitations) take a transaction-scoped advisory lock first; concurrency is tested in `engine/tests/test_tenancy_concurrency.py` because pgTAP runs in one session. Settings forms send the organization they were rendered for as a hidden `organization_id`, which the actions only compare with the session's active organization. Later steps change helper bodies, never the existing policies. Reference data (`countries`, `currencies`, `ramadan_windows`, `public_holidays`) is global, select-only and seeded from `engine/src/maqdar_engine/synth/data/*.csv` through `maqdar-synth emit-reference-sql` (a test keeps them in sync). `demand_history` is partitioned by month into the `partitions` schema and deliberately has no foreign keys (bulk-load speed); the import path checks references and deletes demand rows before an organization. Default privileges in `public` are revoked (hosted projects stop auto-granting new tables and sequences on 2026-10-30), so every new table, sequence and function gets explicit grants and revokes; `supabase/tests/0020_table_privileges.test.sql` snapshots them.
- **Master data UI.** Every master-data screen is an entity definition in `apps/web/src/lib/master-data/entities/` registered in `registry.ts`; routes are thin wrappers around `ListScreen` / `EditScreen` (`src/components/master-data/`), and writes go through the two Server Actions `saveEntity` / `deleteEntity`. Lists are server-rendered with URL state (allow-listed sort and filter params, page sizes 25/50/100), filter `.eq('organization_id', getActiveContext().active.id)` explicitly, use `count: 'exact'` and redirect on `PGRST103`; from row 1,000 on they count first and read the page from the nearer end of the order (`nearestRange`), so the last page costs as little as the first. Search matches tokens from `normalizeSearch` (mirror of `app.normalize_search`, shared fixtures in `supabase/tests/fixtures/normalize_search.json`) against the stored `search_text` column. Item references are typed as part codes with suggestions from `/api/lookup/items`; never query Supabase from the browser (it would refresh single-use refresh tokens). Edits carry `updated_at` for optimistic concurrency. Items and locations with `demand_history` cannot be hard-deleted (MQ409); supersession and location-parent cycles raise MQ422 with the field in the error hint.
- **Import format.** `engine/src/maqdar_engine/importformat.py` is the contract for every CSV import (natural keys, no organization id in files). Regenerate the outputs after changing it (from `engine/`): `uv run maqdar-synth format --markdown --write` (replaces the block between the markers in `docs/import-format.md`; run prettier on it afterwards), `uv run maqdar-synth format --json --write` (writes `docs/import-format.schema.json` and its byte-identical copy `packages/shared/src/import-format.schema.json`, both prettier-ignored) and `uv run maqdar-synth format --sql` (paste the seed, with its two marker lines, into the import wizard migration; pytest keeps all of them in sync).
- **Imports.** The wizard (`/imports`, editors only) parses files in a browser Web Worker (`src/lib/imports/parse.worker.ts`: Papa Parse, SheetJS 0.20.3 from its CDN tarball, loaded client-only through `import-wizard-loader.tsx`), normalizes cells to canonical contract strings and sends JSON chunks through thin route handlers under `/api/imports` to the definer RPCs `import_create_batch`, `import_stage_chunk`, `import_seal_file`, `import_commit_step`, `import_resume`, `import_cancel_step` and `import_delete`. All validation and merging is set-based SQL against the contract seeded into `ingest.contract_*`; staging lives in the private UNLOGGED schema `ingest` (no API role usage). `import_batches`, `import_files` and `import_errors` are RPC-only and readable by editors only, like the Storage originals in the private `imports` bucket (paths generated by the server; uploads and deletes bound to them by policy). Batches of up to 5,000 staged rows commit all-or-nothing, larger ones in resumable steps; every import demand write and `app.refuse_delete_with_demand` share the advisory lock `maqdar.import:<org>`, and merge targets are analyzed before units when their statistics are stale. Demand partitions are never created at runtime. State-changing cookie routes require a same-origin `Origin`, `Content-Type: application/json`, `Cache-Control: private, no-store` and a body cap; signed-out `/api/*` fetches get a 401 JSON (navigations still redirect to `/login`). The browser talks to Supabase only by a plain `fetch` PUT to a signed upload URL. Import messages (`ImportsClient`, `ImportErrors`) are provided by `src/app/(app)/imports/layout.tsx`, not the root provider. Never run `supabase config push` (it would send local settings such as the 50 MiB upload limit to the hosted project).
- **Synthetic data.** `maqdar-synth` only ever targets loopback hosts; never point it or the Supabase MCP tools at the hosted project for data. The loader analyzes each master table right after its `COPY`, because stale statistics turn child foreign-key checks into scans (`docs/performance.md`); bulk imports must do the same. Presets, demand model and calendar sources are in `docs/synthetic-data.md`.
- **REST API.** `/api/v1` authenticates with scoped API keys and bypasses cookie-session refresh. Settings lets owners/admins create expiring keys (shown once, only SHA-256 stored) and revoke them. A key requires its creator to remain an owner/admin. The sole service-role data client is `src/lib/supabase/api.ts`, restricted by ESLint and isolation tests to the API runtime; it calls only `api_organization`, `api_list`, `api_list_demand`, `api_upsert`, `api_handoff_list`, `api_handoff_get`, `api_handoff_acknowledge`, `api_handoff_acknowledgements`, `api_transfer_handoff_list`, `api_transfer_handoff_get`, `api_transfer_handoff_acknowledge`, `api_transfer_handoff_acknowledgements`, `api_event_purchase_handoff_list`, `api_event_purchase_handoff_get`, `api_event_purchase_handoff_acknowledge`, `api_event_purchase_handoff_acknowledgements`, `api_excess_disposition_handoff_list`, `api_excess_disposition_handoff_get`, `api_excess_disposition_handoff_acknowledge` `api_excess_disposition_handoff_acknowledgements`, `api_network_handoff_list`, `api_network_handoff_get`, `api_network_handoff_acknowledge` and `api_network_handoff_acknowledgements`. Each RPC derives the organization from the key and filters it explicitly. Upserts reuse the import validators and merges in one transaction; changed writes appear in Imports with source `api`. Never log raw database/exception messages, bodies or credentials. The contract generates `src/lib/api/openapi.json` via `pnpm --filter web gen:openapi`; tests detect drift. Read `docs/api.md` for limits, paging, retries and rollout. Database suites share tables and statistics: run pgTAP, pytest database tests and Playwright sequentially.
- **Tests.** Vitest for logic (`*.test.ts` next to the code), Playwright in `apps/web/e2e` against the local stack, pgTAP in `supabase/tests` (`<nnnn>_<name>.test.sql`, every file wrapped in `begin … rollback`), pytest in `engine/tests` (`statistical` tests use the medium preset; `db` tests need `MAQDAR_TEST_DSN`).
- **CI** (`.github/workflows/ci.yml`) runs web checks, the Supabase job (pgTAP, types check, tiny synthetic load with its database tests, build, Playwright against `supabase start`) and the engine job. No repository secrets are needed for the local-stack jobs.
- **Shell on Windows.** Commands longer than about 8 KB fail to parse in the Bash tool; write large files with the file tools, not heredocs.

- **Transactions and dashboard (Step 6).** Stock snapshots, open orders and receipts extend import v1 additively and use transaction API scopes; their UUID pages and atomic writes are capped at 1,000 rows. Receipts never mutate stock or orders. `dashboard_summary` is SECURITY INVOKER and preserves branch RLS. Currency totals remain separate and decimal strings remain exact through display. Business audits are append-only to API roles; demand writes are statement summaries. pg_cron maintains forward partitions and bounded staging/error cleanup; the separately enabled Storage retention workflow removes originals through the Storage API after 30 days. See `docs/transactions-dashboard.md` for rollout and definitions.

- **Planning runs (Step 7).** `planning_runs` is session-readable with tenant and location RLS; only guarded enqueue/cancel RPCs accept editor requests. The private pgmq queue and `planning.leases` are never exposed to API roles. `maqdar-worker` uses a dedicated database login with membership in the NOLOGIN `maqdar_worker` capability role and only nine private worker RPCs. Read `docs/planning-runs.md` for leases, retries, bounds and owner-run rollout. Do not start a hosted worker or provision credentials from this task.

- **Scoped simulation runtime.** `maqdar-simulation-worker` uses only five scoped RPCs and the separate NOLOGIN `maqdar_simulation_worker` capability. Database-owned login OID/name bindings select the organization before queue mutation; global claim skips bound simulations even while paused. Never grant the runtime the global capability, raw tables or arbitrary role memberships. The separate Cloudflare service defaults to paused/probe; it does not deploy through `maqdar-web`. Read `docs/acme-simulation-worker-deployment.md` for the three-file owner-reviewed rollout, restricted credential, probe, activation and recovery. No hosted deployment/provisioning is authorized by preparing this implementation.

- **Demand classification (Step 8).** `classification_enqueue` requires explicit complete-history confirmation and validated thresholds. The worker captures private immutable sufficient statistics through `planning_task`, computes `daily-v1` with Decimal arithmetic, and publishes atomically through `classification_finish`. `demand_classifications` is session-readable with tenant/branch RLS and no API writes; snapshot item identities intentionally survive catalog edits/deletion. Read `docs/demand-classification.md` for definitions and upgrade order.

- **Forecast baselines (Step 9).** `forecast_enqueue` requires confirmed history and 1–100 selected item codes. The worker captures immutable sparse daily inputs through `planning_task`, compares seven fixed baselines with three rolling backtests, and publishes through `forecast_finish`. Results retain source evidence and tenant/branch RLS. Read `docs/forecast-baselines.md` for model definitions, bounds and owner-run upgrade order.

- **Forecast expansion (Step 9b).** `expanded-v1` adds bounded StatsForecast ETS/ARIMA candidates and seeded empirical daily bootstrap bands with a separate historical coverage exercise; see `docs/forecast-expansion.md`. `forecast_expanded_enqueue` allows at most 10 items and uses a 900-second lease; its numerical child process times out after 720 seconds. Baseline-v1 remains available with its original 100-item/120-second bounds. Pinned numerical dependencies require `uv sync --locked`. Never change a versioned method silently; automatic fitting uses floats while original source and baseline arithmetic remain Decimal.

- **Demand preparation (Step 10).** `preparation_enqueue` requires confirmed history for all related sources and 1–25 selected codes. The immutable capture expands effective-at-cutoff supersessions and two-way interchanges to at most 100 sources; `preparation-v1` converts each source once to terminal units and records daily calendar evidence. Conflicting groups are blocked, one-way substitutes remain separate, and unverified calendar dates stay unknown. Results are tenant/branch scoped and published through `preparation_finish`. Read `docs/demand-preparation.md` before changing graph/calendar semantics.

- **Prepared-group forecasts (Step 10b).** `regional-v1` forecasts one saved ready preparation group with explicit fixed-group confirmation. The group, conversions and historical flags remain fixed across comparisons; each model fits demand only from its training prefix. A bounded weekday/holiday/Ramadan candidate competes with the existing nine models. Unknown dates receive no event adjustment. Future calendar references are captured once and reused on retry. It reuses forecast RLS, the seven worker capabilities and expanded forecasting's 900-second lease/720-second child-process limit. Read `docs/prepared-forecasts.md` for lifecycle gaps, numerical bounds and conditional coverage interpretation.

- **Inventory policies (Step 11).** `policy-v1` consumes one selected saved forecast with fixed calendar-day lead time, review interval and cycle-service probability. `policy_enqueue` captures source evidence at enqueue, and `policy_finish` adds the eighth worker capability. Conditional thresholds use seeded daily error paths; they do not sum daily interval endpoints or execute orders. Read `docs/inventory-policies.md` for calibration, lifecycle, units and bounds.

- **Policy review workbench (Step 12a).** Proposals never mutate calculated policies; review requires a different authorized user, and worker permissions remain unchanged. Read `docs/policy-workbench.md` for review rules, persistence and rollout.

- **Planning KPIs (Step 12b).** `dashboard_kpis` and `forecast_quality` use invoker rights and existing tenant/branch RLS. Stock availability divides positive observed pairs by all observed pairs, with missing/stale coverage explicit. Forecast scores remain saved model-selection scores; coverage identifies its separate historical evaluation model and window. No cross-item error averages or current-catalog unit inference. Read `docs/planning-kpis.md` for filters, semantics and owner-run rollout.

- **Stock comparison (Step 12c).** Demand/stock units are optional source claims; legacy observation updates without a unit clear prior provenance. New individual forecasts/policies capture consistent labels immutably and conflicting units block calculation. Compare only an explicitly selected calculated maximum or approved revision at the saved cutoff, with matching known units and a snapshot at most seven days old. Use exact SQL numeric and decimal strings; unavailable is distinct from zero. Read `docs/stock-comparison.md` for semantics and rollout.
- **Prepared stock comparison (Step 12d).** New preparations capture lifecycle-eligible demand-unit statistics. Prepared forecasts/policies retain saved two-way 1:1 pool eligibility and member evidence. Every member needs a matching-unit snapshot within seven days at the cutoff; deficits reduce pooled availability and missing members invalidate the whole comparison. Physical inventory values are contextual and separated by currency; pooled-excess valuation is deferred. Read `docs/prepared-stock-comparison.md` before changing pooling semantics.

- **Replenishment drafts (Step 13).** Individual-item drafts require explicit maximum selection, exact-cutoff known-unit stock, complete synchronized inbound confirmation and additional unallocated backorders. All positive remaining open inbound counts; receipts are never subtracted again. Saved evidence is immutable and freshness-checked; draft writes are editor-only with tenant/branch RLS. Read `docs/replenishment-drafts.md` for limits, timing caveats and rollout.

- **Supplier scenarios (Step 13b).** MOQ/pack scenarios use a saved draft's gap, explicit supplier selection, supplied matching units, matching fixed lead time and confirmation of terms at cutoff. Zero gaps stay zero; use exact quotient/remainder rounding for positive gaps. Supplier terms are unversioned; scenarios capture evidence and never place orders or recalculate stock/policies. Read `docs/supplier-scenarios.md` for compatibility and rollout.

- **Delivery scenarios (Step 13c).** Saved supplier quantities and calendar-day lead times stay fixed. Confirm applicability, move order and receipt independently to known working dates, and stop at the first unknown within each 90-date search. Receipt beyond cutoff plus saved lead flags policy recalculation without changing the policy. The guarded definer preview preserves membership, active-claim and branch scope; calendar helpers remain private. Read `docs/delivery-scenarios.md` for evidence, coverage limits and rollout.

- **Purchase-cost estimates (Step 13d).** Use saved delivery quantities/dates and the exact saved supplier-item identity, matching supplied units and a finite price-valid-from date no later than adjusted order. Confirm current price applicability, multiply exact numerics and round once half-up to reference currency precision. Preserve source policy warnings and immutable price evidence; no landed-cost adjustments or orders. Read `docs/purchase-cost-estimates.md` for limits and rollout.

- **Purchase review (Step 14).** Submit positive available estimates for independent reasoned review. One pending proposal per original draft; latest approval is selected while earlier decisions remain. Recheck current price fingerprints at submission/approval, and require an explicitly false saved policy-recalculation flag to approve. Authors may withdraw after demotion while still authorized members. Approval is a planning selection and never creates orders or inbound. Read `docs/purchase-review.md` for access, replay, concurrency and rollout.

- **Purchase handoffs (Step 15).** One immutable CSV/JSON planning handoff per approved proposal. Editors create; scoped members read/download. New records require current selection, matching price evidence and a false policy-recalculation flag. Existing retries retain original evidence; newer approvals make earlier handoffs historical. Downloads never place orders or add inbound. Keep versioned serializers stable and read `docs/purchase-handoffs.md` for file semantics, concurrency and owner-run rollout.
